# CSR vs SSR, and Vite vs Next.js

**2026-08-16** — whether the client should stay a Vite-built client-rendered SPA
or move to Next.js with server rendering.

**Decision: stay on Vite + CSR.** The conditions that would reopen this are
listed at the end.

---

## What the app actually is

Production has exactly **one route**. `apps/web/src/app/router/app_router.tsx`
mounts `/` → `MapPage`, a catch-all redirect back to it, and a set of dev-only
routes that `__IS_DEV__` strips from the production build. Everything a user sees
is one React Three Fiber canvas.

That single fact settles most of the question, because server rendering is a
technique for producing HTML, and this application's screen is not HTML.

## Why SSR has nothing to render

The visible surface is a WebGL canvas whose contents are computed by the GPU on
the client. Server-rendering it produces an empty `<canvas>` element.

React Three Fiber makes this explicit rather than merely impractical: `<Canvas>`
cannot render on the server at all. A Next.js port would have to wrap it in
`dynamic(() => import(...), { ssr: false })` — **disabling SSR for 100% of the
meaningful application**, after paying the full cost of adopting a framework
whose headline feature is SSR.

SEO doesn't rescue it either. One route, no indexable text. There is nothing for
a crawler to collect that a static `index.html` doesn't already give it.

## The real first-paint problem is a different shape

What actually stands between a cold visit and the first rendered frame:

```
empty #root → parse 655 kB of JS → init WebGL → fetch tiles (~21 kB each)
            → build meshes → first frame
```

SSR touches none of it. It would paint a shell marginally sooner and change
nothing else.

And that shell is available for free right now: `apps/web/index.html` ships
`<div id="root"></div>` **completely empty**, so the page is blank until JS
executes. Putting a static loading shell directly in that div captures most of
the perceived-performance benefit people go to SSR for, at the cost of a few
lines of HTML.

The other lever is code-splitting the Three/R3F bundle behind a dynamic import.
That is a Vite configuration concern. Neither of these needs a framework.

## What Next.js would cost here

- **The Deno workspace stops being uniform.** `apps/web`, `apps/api`, and both
  packages are currently one Deno workspace, driven by `@deno/vite-plugin` —
  something `README.md` states as a property of the project. Next.js is not a
  first-class Deno target, so `apps/web` would likely split off onto a Node/npm
  toolchain.
- **Staying serverless forces `output: 'export'`**, which disables ISR,
  middleware, server actions, and image optimization. What survives is
  file-based routing — for one route.
- **It pulls toward Vercel**, which
  [20260816-deployment-hosting.md](./20260816-deployment-hosting.md) rejected for
  concrete reasons (CORS management, the Hobby plan's non-commercial clause).
  Running Next on Cloudflare instead requires the OpenNext adapter, i.e. another
  moving part.

Against that, the benefit column is currently empty. API routes / BFF would be
genuinely useful once a product layer (chat, presence, accounts) exists — but
that is also the moment a real server is needed, and `apps/api` already runs
Hono. Adding Next as a BFF then would just add a second server.

## Prior art: Figma

Figma is the same shape of application — a professional canvas tool in the
browser — at a scale where the answer has been stress-tested.

Its editor is entirely client-rendered. The renderer is C++ compiled to
WebAssembly via Emscripten, drawing through WebGL implemented from scratch
rather than through HTML, SVG, or 2D canvas APIs (now migrating to WebGPU). The
surrounding panels and UI are React + TypeScript. The split is the same one this
project already has: DOM outside the canvas, GPU inside it.

Figma *does* have server-side rendering — of an entirely different kind. The same
C++ renderer is also compiled natively to x64/arm64 and run headlessly to
generate thumbnails and exports. That is offline image rendering, not HTML SSR.

In a canvas application, the thing worth rendering on a server is a picture,
not markup. This project already has the front half of
that pattern — the bake pipeline is a server-side renderer producing artifacts,
they just happen to be tile binaries rather than images. If shareable location
previews are ever wanted, extending that is the move; server-rendering the React
app is not.

It is also worth noting what makes Figma's version cheap: one renderer codebase
targeting both WASM and native. TypeScript cannot give that property. The parked
Rust/WebGPU migration could — one more entry for that migration's benefit column,
not an argument to restart it.

## Follow-up work this produced

Not framework decisions — just the two things that actually move first paint:

1. A static loading shell inside `index.html`'s `#root`, so a cold visit isn't
   blank until JS runs.
2. Code-split the Three/R3F bundle out of the 1.97 MB (655 kB gzipped) entry
   chunk.

## What would reopen this

- **An indexable content surface** (a landing or marketing page). Even then the
  cheap answer is a separate static page, not migrating the engine's host.
- **Shareable deep links wanting social previews.** That is an OG *image*
  generation problem — an edge function, or the headless-render path Figma uses —
  not SSR.
- **Auth and per-user server state.** This is the real one, and it is worth
  stating precisely, because it is easy to mis-frame: gaining a server does not
  make SSR useful for a canvas — the canvas still renders empty. What changes is
  that **the serverless constraint disappears**, which reopens "where does the
  BFF live". The answer would probably still be Hono rather than Next.

  Three concerns get conflated under "auth" and are more separable than they
  look: **identity** (who is this), **persistence** (placed objects leave
  `localStorage` and belong to someone), and **visibility** (other people see
  your builds). Persistence and visibility are achievable without identity, via
  an anonymous device ID — and visibility is the actual product. Real accounts
  are forced only by cross-device continuity and by moderation enforcement, the
  latter already out of scope.

  Note also that the split stays clean: tiles are immutable and user-independent,
  so they remain static regardless. Only the object layer and identity would need
  a server.
