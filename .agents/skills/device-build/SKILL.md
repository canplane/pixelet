# Building for a device

`apps/native` is the shell as a React Native app with the Rust kernel linked
in, every route from the live deployment. Its native projects, `apps/native/ios/` and `apps/native/android/`, are
generated by `expo prebuild` from `app.json`, the config plugins under
`apps/native/plugin/` and the module under `apps/native/modules/platform/`,
and are not kept: a fresh checkout or worktree has neither until it is
prebuilt.

There is no task that builds the kernel ahead of the app. Each platform's
build runs `apps/native/script/build-native.ts` itself — the pod's "Build the
kernel" phase on iOS, a Gradle task per variant on Android — for the
configuration and system being built: Debug with the kernel's `dev` settings,
Release without, as a deployed page is. cargo is a no-op when the Rust has not
changed. Both find cargo and Deno at `~/.cargo/bin` and `~/.deno/bin`.

A **Release** build embeds the JavaScript bundle and runs without Metro. A
**Debug** build loads it from Metro (`deno task dev:native`) on port 8081, and
only one Metro can hold the port — check that the running one serves the tree
you mean before trusting what a Debug build shows.

A build CI did not number labels itself `#<n>-<commit>`: the last number
this checkout saw published, then what it was built from
(`apps/native/metro.config.ts`), fixed in the bundle when Metro makes it. The
`<n>` is a cache, `apps/web/.build_number`, which a deploy through CI never
writes, so bring it up to date before a Release:

```bash
deno task sync:build-number
```

It reads the build log in the bucket and writes only that cache
(`script/build-log.ts`). A build made before a deploy carries the number
before it, whatever is deployed after; to carry the new one, deploy first.

## iOS

### Once per machine

- Xcode with a signing team for a phone, CocoaPods, Node (for Expo's native
  build), and the Rust targets, which `rust-toolchain.toml` installs.
- Node, as `apps/native/package.json`'s `engines` asks, on `PATH` for `pod
  install`, whose scripts call `node` by name, and named for Xcode's script
  phases in `apps/native/ios/.xcode.env.local` (`export NODE_BINARY=…`),
  which prebuild does not write. Node runs only that toolchain: its
  bundling phases run Expo's CLI, which loads the app's TypeScript configs
  with Node's own type stripping (22.18 on). Every task of the tree runs
  under Deno.

### Generate

```bash
(cd apps/native && deno install && deno run -A npm:expo@57.0.25 prebuild --platform ios --no-install)
(cd apps/native/ios && pod install)
```

Again after anything under `modules/platform/` gains a file (a new Swift
file is added to the pod only by `pod install`), after `app.json` or a plugin
changes, or after a dependency is added.

`plugin/ios-build.ts` sets the iOS the pods and the app target: the highest
floor of what the app links, which its dependencies decide. A target is where
a build links, not a promise of what runs.

### Build, install, launch

From `apps/native/ios`. The phone's xcodebuild id and its devicectl id differ;
`xcrun devicectl list devices` gives the second, `xcrun xctrace list devices`
the first.

```bash
xcodebuild -workspace pixelet.xcworkspace -scheme pixelet -configuration Release \
  -destination 'id=<xcodebuild id>' -derivedDataPath build/derived \
  DEVELOPMENT_TEAM=<team> CODE_SIGN_STYLE=Automatic -allowProvisioningUpdates -quiet
xcrun devicectl device install app --device <devicectl id> build/derived/Build/Products/Release-iphoneos/pixelet.app
xcrun devicectl device process launch --terminate-existing --device <devicectl id> me.plei.pixelet
```

For the simulator: `-configuration Debug -destination 'id=<simulator id>'`
with no signing, then `xcrun simctl install booted
build/derived/Build/Products/Debug-iphonesimulator/pixelet.app` and `xcrun
simctl launch booted me.plei.pixelet`. The kernel phase builds the
simulator's target itself.

Xcode itself builds the same thing: open `ios/pixelet.xcworkspace`, with a
team to sign with for a phone.

`--console` on the launch streams the app's stdout, where the kernel's last
words go (`[pxl] …`).

A device draws its text at the size the phone's Text Size setting asks for,
which a page ignores, so a view that fits on a page can overflow on a device
set larger. The simulator takes the setting from the command line; the two
ends are the ones worth a look:

```bash
xcrun simctl ui booted content_size extra-small                            # the smallest
xcrun simctl ui booted content_size accessibility-extra-extra-extra-large  # the largest
xcrun simctl ui booted content_size large                                  # the default
```

### An Apple Vision Pro

The iPhone app runs on visionOS as it is, in a window, as an iPhone app
there does ("Designed for iPad/iPhone"): the same build for the iPhone's SDK,
the kernel drawing through Metal. A native visionOS target is not made here:
the platform module is an Expo module, and Expo builds for no visionOS.

In the simulator, once Xcode has the runtime (`xcodebuild -downloadPlatform
visionOS`), the Vision Pro simulator's id is a destination of its own, and
the products are the iPhone simulator's:

```bash
xcodebuild -workspace pixelet.xcworkspace -scheme pixelet -configuration Release \
  -destination 'id=<Vision Pro simulator id>' -derivedDataPath build/derived
xcrun simctl install <id> build/derived/Build/Products/Release-iphonesimulator/pixelet.app
xcrun simctl location <id> set 37.2741,127.0437
xcrun simctl launch <id> me.plei.pixelet
```

A Release, since the simulator reaching Metro has not been tried. It has
drawn the terrain from the served tiles and named the place. A headset has
not run it yet.

### What has gone wrong

- **"Unable to find a destination"**: the phone dropped off; `devicectl list
  devices` shows it `unavailable`. Reconnect or unlock it.
- **Install works, launch fails "could not be unlocked"**: the phone is
  locked. Unlock it and launch again.
- **Debug fails to link on `facebook::react::Sealable`**: React Native's
  prebuilt core was left as its Release build under a Debug app. The
  prebuilt-flavor plugin marks it as of no configuration on every `pod
  install`, so it should not recur; if it does, `printf None >
  Pods/React-Core-prebuilt/.last_build_configuration` (and the same in
  `Pods/ReactNativeDependencies/` and `Pods/`, Hermes's) and build again.

## Android

### Once per machine

- Android Studio. In its SDK Manager: **SDK Tools** — NDK (Side by side),
  CMake, Android SDK Command-line Tools; **SDK Platforms** — the platform and
  an **ARM 64 v8a** system image (the 16 KB page size one, as new phones
  are) for an emulator. Accepting the licenses is the person's to do.
- An AVD from that image (Device Manager), or a phone with USB debugging on.
- **JDK 17.** A newer one (Android Studio's own is 25) fails the NDK's native
  build of expo-modules-core with "A restricted method in java.lang.System
  has been called". `apps/native/.java-version` names 17 for jenv:
  `jenv add <JDK 17 home>` once, and Gradle run under `apps/native` gets it
  (`jenv exec ./gradlew …`, or `JAVA_HOME` set by jenv's export plugin).
  `plugin/android-build.ts` writes Gradle's daemon criteria
  (`android/gradle/gradle-daemon-jvm.properties`) for 17, so the daemon
  runs on a 17 Gradle finds whatever launches it; opening the project in
  Android Studio once wrote them for its own Java 25, which outranks
  `JAVA_HOME`, and the same failure followed.
- The Rust target `aarch64-linux-android`, which `rust-toolchain.toml`
  installs.

### Generate

```bash
(cd apps/native && deno install && deno run -A npm:expo@57.0.25 prebuild --platform android --no-install)
```

`plugin/android-build.ts` writes what the build is for into
`gradle.properties`: arm64-v8a alone, since the kernel is built for no other
ABI and an APK carrying one without it dies on those phones, and the SDK
floor of the Vulkan this build takes for wgpu.

expo-horizon-core's plugin splits the app into two flavors, `mobile` for a
phone and `quest` for a Meta Quest, so every variant is named for both:
`mobileRelease`, `questDebug`. The `quest` flavor's own manifest
(`android/app/src/quest/`) removes the permissions Horizon's store refuses and
requires head tracking, which no phone has, so a phone takes only `mobile`.
`android-build.js` names the flavors' debug variants to React Native as
debug builds, since it knows a debug build only by its whole name and bundles
any other.

### Build, install, launch

From `apps/native/android`, with `ANDROID_HOME=~/Library/Android/sdk` and
the platform tools' `adb`:

```bash
jenv exec ./gradlew :app:assembleMobileRelease
adb install -r app/build/outputs/apk/mobile/release/app-mobile-release.apk
adb shell am start -S -n me.plei.pixelet/.MainActivity
```

`./gradlew :app:installMobileRelease` builds and installs in one; a bare
`installRelease` is ambiguous between the flavors and fails. The kernel's last
words and panics go to logcat under the tag `pxl`:
`adb logcat -d | grep -E "FATAL| pxl |ReactNativeJS"`.

On an emulator: grant location (`adb shell pm grant me.plei.pixelet
android.permission.ACCESS_FINE_LOCATION`), and put it where there is data —
`adb emu geo fix 126.9780 37.5665` is Seoul; its default is outside Korea,
which draws no terrain. `adb exec-out screencap -p > shot.png` for a look.

### A Meta Quest

The `quest` flavor is the same app as a 2D panel on Horizon OS, which is
Android: `assembleQuestRelease`, or `assembleQuestDebug` for one that asks
Metro, and `adb` as for a phone. It is made for a Quest 3 and 3S alone
(`supportedDevices` in `app.json`): a Quest 2 is left out by choice, not
for anything found failing on one. What differs is the device:

- **Location** comes through expo-horizon-location, expo-location's fork,
  since Horizon OS has no Google Play Services. A Quest has no GPS: the
  position is the network's, and its updates come minutes apart.
- **No compass**: `headingAvailable` finds neither sensor, and the kernel
  never listens for a heading.

No headset has run it. A headset takes `adb` once its developer mode is on
(the Meta Horizon phone app, under a Meta developer account) and it is
plugged in and trusted.

Without one, Meta's Spatial Simulator is an Android emulator for 2D panel
apps. `npx metavr@latest init` signs in to a Meta account, and installs
Meta's agent skills into the home directory besides; it leaves no `metavr`
on `PATH`, so it runs through npx:

```bash
npx metavr tools install spatialsim
npx metavr ssim start    # an emulator adb sees, emulator-5554 if it is the first
adb install -r app/build/outputs/apk/quest/release/app-quest-release.apk
adb shell cmd location set-location-enabled true
adb emu geo fix 127.0437 37.2741
```

Its location is off until turned on, and it has no network provider, so the
position is only what `geo fix` gives. There it has named the place.

### What has gone wrong

- **`dlopen failed: cannot locate symbol …`**: the core named something only
  one system has (it was `os_unfair_lock`). What differs by system is behind
  `cfg(target_vendor = "apple")` / `cfg(target_os = "android")`, and the
  gate clippies pxl-native for both targets.
- **"This app isn't 16 KB compatible"**: a native library aligned for 4 KB
  pages. `build-native.ts` links the kernel with `-z max-page-size=16384`;
  check a build with `llvm-readelf -lW <lib>.so` (every LOAD's alignment
  `0x4000`).
- **`Surface::configure` refuses `Bgra8Unorm`**: Android's Vulkan surfaces
  offer RGBA. The native bracket gives xpute's host the system's preferred
  format (`crates/client-bracket/native/src/surface.rs`), which the kernel
  reads from the device's block, as the page takes the browser's.
- **`Unable to find View for tag: …` from `updateOverflowInset`, seconds in**:
  Fabric never made a view it later reaches, its trace in logcat a
  `MissingViewState` soft exception at the first mount. It was a plain view
  whose flattening changed as a toast's touch came and went (`collapsable`
  in `web/src/platform/web/pill.tsx`); the mount state logged before the
  crash shows what the missing tag holds.
