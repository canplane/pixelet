# The gate that deploys, and what an audit found still pointing at the TypeScript

2026-09-18, after [the server in Rust](./20260918-the-server-in-rust-and-the-line-already-drawn.md)
went live as b15.

## What started it

A question, not a plan: can `apps/api` be deleted now that the Rust serves? The
audit that answered it found one thing that mattered more than the answer.

## What the audit found

`apps/api` cannot be deleted, because it is not one thing. Resolved by import
closure from the tools that are staying, its 58 tracked files fall out as:

|    |                                                                                                |
| -: | :--------------------------------------------------------------------------------------------- |
| 11 | the five Overture ingests, the asset ingest and the brand renderer, and everything they reach  |
|  3 | the texture-pack tool and its manifest pair — `pxl-render`'s `layers.rs` cites its `TILE_SIZE` |
|  3 | the elevation pipeline: bash, SQL, a metadata file                                             |
|  2 | `Dockerfile` (which builds **pxl-geo**) and `deno.json`                                        |
| 17 | the Hono server — `src/app/`, `src/module/**`, the entry points, the vite config               |
| 17 | the bake, ported and byte-compared: terrain, POI, geocode, WKB                                 |
|  3 | scaffolding: `dump_page_source.ts`, `repack_poi_tiles.ts` and the `bake_util.ts` they share    |
|  1 | `category_map.ts`, generated by `script/spec.ts`, every consumer of it now dead                |

So 34 files are dead and 17 are not, and the directory keeps its name while
holding no API. Where the survivors should live is a separate question.

**The finding that mattered was elsewhere.** `.github/workflows/overture-monthly-refresh.yml`
still ran the TypeScript bakes:

```
deno run -A apps/api/src/bake/poi/tool/bake_poi_tiles.ts     --out ./out/poi/v3     --force
deno run -A apps/api/src/bake/geocode/tool/bake_geocode_tiles.ts --out ./out/geocode/v1 --force
```

`cron: 0 3 1 * *`. The cutover moved `deno task dev` and the three `bake:*`
tasks to Rust and never looked at CI, so production's monthly refresh was still
the implementation the day's work replaced — and deleting the TypeScript would
have broken it silently, a fortnight later, in the one job nobody watches.

That is the general shape worth keeping: **a port is done when everything that
invokes it has moved, and CI invokes things.** Reading the source tree finds
callers; it does not find schedules.

## Why CI at all, and why now

The audit's conclusion was that the deletion is gated on CI being switched and
verified. Switching CI without having any CI was the wrong order — so the gate
came first.

There is a second reason, which the day itself supplied. Three of the session's
failures were things a machine checks better than a person:

- The deploy's first attempt died on a sentinel the generated constants had made
  impossible. The guard caught it, but only because a deploy was attempted.
- `/api/*` reached the wrong server for twenty minutes because a bind-mounted
  Caddyfile is read at start, and nothing after the deploy asked whether the
  routes answered.
- The origin was checked by hand, four times, with a `for p in ...; do curl` loop
  pasted from the README and edited each time.

## The shape

**One workflow, three jobs**, rather than a CI workflow and a CD workflow
reacting to it. A `workflow_run` trigger reads its definition from the default
branch and loses the push's context; jobs with `needs:` cannot start against a
commit the gate never saw, and that is the whole property wanted.

| Job             | When                                       | What                                                             |
| :-------------- | :----------------------------------------- | :--------------------------------------------------------------- |
| `gate`          | every push to main, every PR               | `check`, `test`, `lint`                                          |
| `deploy-web`    | main, green                                | `deno task deploy`, then the smoke                               |
| `deploy-server` | main, green, and the server's tree changed | ssh, reset, `up --build --force-recreate`, then the origin smoke |

**The two deploys are gated differently, and the asymmetry is the point.**
Publishing to the edge is idempotent, uploads only changed assets and is
reversible from a dashboard, so it runs on every green push. Reaching into the
production VM over SSH is none of those, so it runs only when `crates/`,
`infra/prod/` or the Dockerfile changed. A docs commit does not touch
production.

`--force-recreate` is in there because of the day's own bug, and the comment
beside it says so: the Caddyfile is a bind mount and a bind mount is read at
start, so `up --build` alone leaves a stale relay in front of a fresh server.

**`deploy-web` is one concurrency group across every ref.** The build number
comes from a single counter object in the bucket, and `deploy.ts` is written
around "this has one deployer" without being able to enforce it. A hand deploy
is still the fallback and is still outside the group — which is now the one way
to collide, and is worth knowing rather than preventing.

## The smoke check is a script, not a list

`script/smoke.ts`, and it is a Deno script rather than curls because the
addresses stopped being hand-kept two commits earlier. It builds the URLs from
the same generated constants the client and the Worker read, the versions from
`published.json` and the asset key from the ingest's own table — so a version
bump or a moved root cannot leave it checking something nobody serves. Pasting a
path list into a workflow would have reintroduced exactly the copy the address
space was collapsed to remove.

It checks the old addresses too. `/api/tiles/…` and `/api/search` must be 404:
a 200 from either means a relay somewhere is still carrying the pre-09-18 shape,
which is precisely the failure that took twenty minutes to see by eye.

`--origin` is the same checks against `api.plei.me` with the bucket's branches
left out, since the origin has never served those.

## What was pinned, and why

- **Rust 1.94**, matching `apps/api/Dockerfile`'s base image. A toolchain
  release turning on a new clippy lint would otherwise fail a push that changed
  nothing.
- **Binaryen 132**, downloaded from the release rather than apt. `wasm-opt`
  prints the import/export mapping the shell imports, and which letters it
  assigns is the optimizer's business — a different version is a different ABI.
  apt's is also years behind.
- **Host key**, when `VM_KNOWN_HOSTS` carries it. The fallback is `ssh-keyscan`
  with a warning annotation, which is trust-on-first-use and worth closing for a
  host that takes a deploy.

`deno lint` needed two `no-regex-spaces` fixes in `script/spec.ts` (from 09-15)
before it could be a gate at all. A lint that has never been green is not a
gate; it is a list.

## Where it stands

In: the workflow, `script/smoke.ts` and its task, the monthly refresh on the
Rust bakes, `deno lint` clean.

Verified before committing: the smoke script against both the edge (12/12) and
the origin (5/5); every shell step through `bash -n`; the path filter against
four real bases, including the force-push and dispatch cases that have none;
the Binaryen URL; and the monthly refresh's exact command chain, run locally
against `_meta/land_pages.json` fetched from the bucket the way CI fetches it.

Not verified, and cannot be from here: the workflow actually running. It needs
its secrets set, and the monthly refresh should be tried once through
`workflow_dispatch` before 10-01 rather than discovered by the cron.

Done since: `apps/api` is deleted and what survived it moved to `tool/`. The
refresh is still unrun — which is a risk taken knowingly, against a checkpoint
branch, rather than the gate the audit called it.
