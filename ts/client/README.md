# @pxl/client

The client is everything around the core: the UI people touch, the services that
answer the core's needs on each platform, and pixelet's assembly of xpute's
runtime, which starts the core. It is one Expo app for iOS, Android and the
web. The world is not here: the client never computes a coordinate or a tile,
it only calls the core and shows what the core tells it.

## Three layers

```text
  ui/         the UI: React Native, the same on every platform
  runtime/    pixelet's assembly of xpute's runtime: the web worker, and
              each platform's boot
     │  ui/ reaches below only through service/; runtime/ takes xpute's
     ▼  packages and the GPU's directly as well
  service/    what answers the core and the UI on this platform
    core/       the core's interfaces: calls, what the core tells the UI,
                surfaces, sensors, text
    sys/        the core's files, the boot's and the GPU's states, the stop report
    origin/     the server the client reads from, and whether it is online
    platform/   what differs by platform, as file pairs
```

The UI reaches the core only through `service/core/`, and beside it reads
directly only the types and constants generated into `abi/`, the build's own
(`build.ts`) and xpute's kit. `service/core/` calls the core over the UI's own
end of the runtime, which the boot opens (`open_ui`, from `@xpute/runtime-web`
on the web and `@xpute/expo` natively) and `runtime/ui.ts` installs as a
`Sender` in `service/core/core.ts`. The bindings and the numbers both sides
read, generated from `spec/`, are in `abi/`. A release build writes each
exported literal where it is read (`babel.config.ts`), so the bundle holds a
method's number and not its name.

## One app, two kinds of platform

What differs between the web and native is a pair of files in
`service/platform/`: `<x>.web.ts` is the web file and `<x>.native.ts` the native
one, and the shapes both share are in `platform/types.ts`. An import names
`<x>.ts`, and Metro and the type-checks pick the right one for each build. Two
pairs stand outside it: the page's at the source's root (`page.web.ts`,
`page.native.ts`), and the one that boots the core in `runtime/` (`boot.web.ts`,
`boot.native.ts`). On the web it opens the worker (`worker.ts`), which
instantiates the core's module and lists what xpute's runtime starts it with.
Natively the core is linked into the app with `pxl-runtime`, the native
counterpart of `worker.ts`, which lists the same for `xpute-runtime-native`, and
that runtime runs the core on a thread of its own. The native runtime outlives a
reload of the UI, which meets the same core as a new UI. A piece of the UI that
the platforms draw differently is such a pair or a file with its override beside
it (`src/ui/shared/component/README.md`). `src/conform.ts` holds each native
file to its web file's exports and each override to its default's.

## The boot

The boot brings the client up from the bottom: it mounts what the UI implements
for the core, starts the core where its platform runs it, and moves where the
boot stands as the core answers, a GPU and the world's source come and the first
snapshots arrive, which is alike on both platforms (`runtime/ui.ts`). The UI
only reads that state, through the services, and shows a cover over the world
until the view is first drawn (`ui/feature/cover/`).

## The app's ABI

xpute carries frames and does not know what they mean; their meaning is the
app's, declared once as interfaces in WIT under `spec/client/core/wit/`, from
which both sides' bindings are generated. Each interface has one end in the
core and one in the services, named alike.

The core names a file only by its path, a tuple of tokens, and the client
decides, once at boot, what answers each path: the services
(`service/sys/fs/`), on both platforms. So no URL, version or storage key
reaches the core, and where the world is read from changes without it.

## Builds

The web build is Expo's, bundled by Metro into one HTML file over one
bundle. `script/wasm-build.py` builds the core's WebAssembly module into
`public/core.wasm`, and `script/wasm-watch.py` rebuilds it while the dev server
runs; `script/web.ts` writes the page's template and serves a preview, and
`script/proxy.ts` forwards the server routes the way the Worker does.

On iOS and Android, the native projects (`ios/`, `android/`) are generated by
`expo prebuild` and not kept; the config plugins in `plugin/` shape them, and
the app's own native module is `modules/platform/`. The core is compiled as a
step of the native build, through xpute's native module.
