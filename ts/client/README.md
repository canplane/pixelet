# @pxl/client

The client is everything around the core: the UI people touch, the services that
answer the core's needs on each platform, and the runtime that runs the core. It
is one Expo app for iOS, Android and the page. The world is not here: the client
never computes a coordinate or a tile, it only carries the core's requests out
and the core's snapshot back.

## Three layers

```text
  ui/         the UI: React Native, the same on every platform
     │  reaches below only through service/
     ▼
  service/    what answers the core and the UI on this platform
    core/       the app's ABI: commands, the snapshot, surfaces, sensors, text
    sys/        the core's files, the boot's and the GPU's states, the stop report
    origin/     the server the client reads from, and whether it is online
    platform/   what differs by platform, as file pairs
     │
     ▼
  runtime/    xpute's runtime, opened where the platform places the core
```

The UI reaches the core only through `service/core/`, and `service/core/`
reaches it only by a command's number and its fields, `core.send(Command.X,
...)`, typed by a table generated from the core's specification, so a field
cannot mean one thing on one side and another on the other. The numbers both
sides read, generated from `spec/` or written beside it, are in `abi/`. A
release build writes each exported literal where it is read (`babel.config.ts`),
so the bundle holds a command's number and not its name.

## One app, two kinds of platform

What differs between the page and a device is a pair of files in
`service/platform/`: `<x>.ts` is the page's and `<x>.native.ts` the device's,
and the shapes both share are in `platform/types.ts`. Metro picks the right one
for each build. The pair that opens the runtime is in `runtime/`: on a page the
core runs in a worker (`open.ts`), and on a device it runs beside the UI, linked
into the app (`open.native.ts`). A piece of the UI that the platforms draw
differently is a file with its override beside it
(`src/ui/shared/component/README.md`).

## The boot

`runtime/boot.ts` brings the client up from the bottom: it opens the runtime,
binds the core's commands to it, and reports where the boot stands as the core
starts, a GPU answers, the world's source is declared and the first snapshots
come. The UI only reads that state, through the services, and shows a cover over
the world until the view is first drawn (`ui/feature/cover/`).

## Builds

The page is Expo's web build, bundled by Metro into one HTML file over one
bundle. `script/wasm-build.py` builds the core's WebAssembly module into
`public/core.wasm`, and `script/wasm-watch.py` rebuilds it while the dev server
runs; `script/web.ts` writes the page's template and serves a preview, and
`script/proxy.ts` forwards the server routes the way the Worker does.

On a device, the native projects (`ios/`, `android/`) are generated by
`expo prebuild` and not kept; the config plugins in `plugin/` shape them, and
the app's own native module is `modules/platform/`. The core is compiled as a
step of the native build, through xpute's native module.
